# Known limits

What the fleet deliberately does not enforce or cover. Each item is a gap that was looked at and left, with the reason, so a deliberate gap is not mistaken for an oversight. Anything here that becomes a rule, a hook or a test leaves this file the same day.

## The board hooks

**Failure and cancellation never reach Blocked.** `SubagentStop` carries no `status` field, so `board-subagent-stop.sh` cannot detect a failed or cancelled run. The read is kept for forward compatibility and the docs do not claim it works. The route to Blocked that does work is a `Blocker:` line in the handoff. `agent_transcript_path` is present on every `SubagentStop` event and the hook already walks it to tell a schema spawn from a silent run, so what is missing is narrower than a new reader: teaching the existing one to recognise a failed or cancelled run.

**Binding is one item per checkout, not per agent.** The hooks read the checkout's `.boards/.focus`, so every spawn in a focused checkout belongs to that item. Per-agent binding needs a supported correlation between the Agent tool's invocation and the subagent identity in the event, and it must not be done with a shared "latest prompt" file: two agents spawned together would race for the same line. `SubagentStart` does carry `agent_id`, `cwd` and `prompt_id`, which is more to work with than the hooks currently use.

**The transcript reader fails open.** `board-subagent-stop.sh` consults `agent_transcript_path` to tell a schema-spawned run from one that produced nothing, and a transcript it cannot read - missing, unreadable, oversized, unparseable - passes with a log line rather than blocking. Deliberate: deadlocking a subagent is worse than a rare silent pass.

## The scope hook

**It is not a containment boundary.** `enforce-agent-scope.sh` reads shell text, and a shell does not. A program run through Bash writes wherever the process can, and no shell-level check sees inside it. The sandbox in `home/settings.json` is a credential boundary, not a role boundary - its `denyWrite` covers `~/.ssh` and friends, not other repositories. Unattended steward runs need filesystem permissions before they are safe, and the steward is the agent this matters most for. Every entry below is one consequence of that; finding one hole is not evidence there are no others.

**`strip_quoted` pairs quotes naively in the general segmenter.** `echo "say \"x" ; git commit -m x ; echo "the end"` is allowed for `scout`, even though a real shell runs the commit as its own command: the escaped quote inside the first span shifts the parity, and the later quoted `"the end"` gives the naive pairing something to close against, erasing everything between, including the commit. The escape-aware stripper only reaches the interpreter-payload regex; the general command-segmentation path that every `enforce_*` function walks still uses the naive one.

**The 8192-byte scan bound truncates.** `echo <9000 bytes> ; git commit -m x` is allowed, with a log line naming how far over the bound the command was. Without the bound a long enough command blew the hook's 10-second timeout, which renders no decision at all and takes every role's guard down silently with no log. A narrow logged bypass is the trade for an absolute silent one.

**The 16-segment bound truncates the same way, and it is the tighter of the two.** `echo a ; ` sixteen times in front of `git commit -m x` is allowed for `refuter`, with a log line saying how many segments were dropped. Sixteen is generous against real work - the claudecode-agents repo's own scope-hook corpus tops out at four segments - and the bound exists because bytes were never the cost: 200 chained `git log` steps is 2000 bytes, a quarter of the byte bound, and measures well past the 10-second timeout without it.

**Per-segment word count is unbounded.** `A=1 ` five hundred times in front of `git log` is 2007 bytes and one segment, and measures about 17 seconds against a 10-second timeout. `command_words` spawns two processes per leading assignment or wrapper word and nothing caps how many it walks. The fix is either a third bound or the single-pass rewrite that replaces all three.

**Variable expansion, `eval`, heredocs and other languages' inline-code flags are unreachable.** Any parser reading unexpanded text cannot see them. `python3 -c "import os; os.system('git commit -m x')"`, `node -e` and `perl -e` are all allowed; they are `eval` wearing a different name. The hook recovers payloads from `bash -c` and its four sibling shells only, and its own comment says so.

**Command substitution is unchecked for three roles.** `$(git commit -m x)` and the backtick form are allowed for `refuter`, `coder` and `ui-designer`, because only `fleet-steward`, `scout` and `reviewer` check for substitution. The leading-token strip that closes `{ git commit -m x; }`, `( git commit -m x )`, `! git commit -m x`, `>/tmp/out git commit -m x`, `timeout 5 git commit -m x` and the body of an `if`, `for` or `while` cannot reach a substitution, because the word has no leading token to remove. `script -q /dev/null git commit -m x` stays open on purpose: `script` puts its typescript file between itself and the command, so listing it as a wrapper would close nothing, and `script cat` would then read as `cat` while actually creating a file called `cat` - the same asymmetry that keeps `sudo` off the wrapper list.

**The refuter's "Never write inside the project" is not enforced against Bash.** `lib/check-write-scope.py` only ever sees `Write`, `Edit`, `MultiEdit` and `NotebookEdit`, so `echo mutated > claudecode-agents/agents/coder.md`, `cp /tmp/x claudecode-agents/workflows/review-round.js` and `rm -rf claudecode-agents` are every one of them allowed. `enforce_fleet_steward` resolves and checks redirection targets for an equivalent rule, so the pattern exists in the same file, and applying it here would still only reach redirections rather than `cp` or `rm` - which is why it is a design question rather than a missing line.

**An `agentType`-less lane is governed by nothing.** The `SubagentStop` matcher skips it and every branch of `enforce-agent-scope.sh` keys on an agent name, so "read-only git only" in a lane prompt is an instruction to a model, not a boundary. The four mechanical lanes in the workflows have always been in that position - they run the project's test suite - and `review-round`'s two git lanes are in it too. Widening `scout`'s or `reviewer`'s allowlist instead would weaken a role boundary for every run rather than for the one workflow that needs `worktree`, `merge-base` and `rev-parse`. A probe spawn that falls back to a non-fleet agent type can run `git commit --allow-empty` in the main checkout and it lands with no refusal.

**A named, non-isolated spawn escapes the fleet entirely, and it is the likeliest shape of a trample.** Spawning a fleet agent with a `name` and no `isolation` puts it on the teammate path, where the hook events carry the name as `agent_type`: `enforce-agent-scope.sh` then allows everything, because no agent type it knows means the main session; the `SubagentStop` matcher never matches; no worktree is cut. A named `coder` commits straight to main with no refusal anywhere. A named read-only agent loses its whole output instead: idle notifications arrive in place of a result, the stop gate's exit 2 has nowhere to deliver, and the run looks like a success with a formatting hiccup. So a named spawn loses whichever half of the contract the role depends on, and neither failure is loud. The refusal branch of the worktree guard may be unreachable from a real typed spawn - a typed `coder` always gets a worktree, and only the ungoverned path ends up in the main checkout - which makes the teammate path the whole risk. Until the hook can key on something a teammate cannot rename, the rule is operational: never name a fleet spawn, and treat a teammate running a fleet body as ungoverned. The lead's body says so.

## Never run against a live Claude

**The refuter.** Its permissions are pinned by 85 deterministic checks in the scope hook suite and its evals exist, but no stubbed suite can show whether an agent given that body actually refutes rather than reviews. `evals/refuter/` probes both directions - a change with a genuinely vacuous test, and a change with nothing wrong where inventing a finding is the failure - and until it runs, the role is a design rather than a capability.

**`fix: true` in `review-round`.** Every branch is covered by deterministic tests that stub the model out, which is exactly the coverage that can hide a gate bug for a fortnight. What those cannot prove: that the git lanes report `isMain` correctly off `git worktree list --porcelain`, that `coder` follows the `git switch` instruction, and that `parallel()` returns lanes in a shape the tests-lane lookup finds. The lookup is by name rather than by position for that reason.

**`refute: true` and the refutation stage.** Same coverage, same gap. What the stubs cannot prove: that a refuter asked to attack a change copies out of the project rather than mutating the tree under test, and that `readHandoff` on a real refutation finds the `Blocker:` lines the way the fixtures say it will.

**Worktree isolation for a workflow-spawned `coder`.** An Agent-tool `coder` spawned with the fleet type gets a locked linked worktree and its commit stays on the per-agent branch, with or without an explicit `isolation` argument, because the harness honours the definition's frontmatter. `review-round` cuts its own worktrees through `worktree.baseRef`, which is a separate mechanism, and that path has not been run live in a repository with a remote. `baseRef` defaults to `fresh`, which branches from `origin/<default-branch>`, so a repository with no remote cannot cut one at all. The cost is load-bearing: `enforce_coder` refuses a writing git command outside a linked worktree (`claudecode-agents/hooks/README.md` item 18), so if isolation does not hold, `coder` stops rather than committing to a shared checkout. That is the intended failure, and it means loop work built on `fix: true` may not run at all until this is settled.

## Refutation checks that do not exist

**Nothing checks that a refutation contains mutation evidence.** `review-round` stops on a `Blocker:` line and on an empty refutation, and treats everything else as unbroken. It never looks at whether the Done section says anything was mutated. A refutation whose only Done bullet is "I read the diff and it looks fine to me" returns `stopped: "clean"` and `approved: true`, which is the exact failure the role exists to prevent, arriving through the gate rather than around it. The check is deferred on purpose: it would have to pin a workflow decision to `coder`'s Done-bullet wording, and a format obligation invented and depended on in one commit is how format obligations decay. It gets built once there is a real refutation handoff to parse, which needs the live runs above.

**The mutation budget per round is unbounded.** A refuter on a large repository runs the suite once per mutation, and nothing caps how many it tries or reports what it dropped.

## Skills

**`using-memory` is not in the fleet.** Its canonical copy is `agent-memory-js/plugin/skills/using-memory`, beside the hooks it documents, so the commit that changes the behaviour is the commit that updates the doc - the same co-location rule that makes `skills/glossary` canonical here. That text says "this plugin's hooks auto-recall", which is false for fleet agents: they reach memory through the connector with no hooks, and only the lead and `researcher` write. Bringing it in means an adaptation plus adding it to ten bodies, the roster, contract section 1.4 and the roster-contract allowlist, and that is its own piece of work. Until then the labelling convention rides in the two bodies that write (design section 6).
